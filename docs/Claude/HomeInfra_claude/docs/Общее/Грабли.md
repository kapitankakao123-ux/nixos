# Грабли и что они означают

Реальные ошибки с этой миграции. Полезны не столько сами рецепты, сколько принципы за ними.

## `does not provide attribute 'nixosConfigurations."X"'`

Имя после `#` — это **имя конфигурации во flake**, не хост и не пользователь. Без `#` подставляется текущий hostname.

Лечение: привести к одному имени `nixosConfigurations.<имя>` и `networking.hostName`. Посмотреть, что объявлено: `nix flake show ~/nixos`.

## `The option '...' does not exist`

**Модуль = объявление опций.** Пока модуль не в `imports`, любая его опция не существует, даже если синтаксис верный. Обратное безобидно: импорт без использования просто ничего не делает.

Так вылезли обе ошибки с DMS: сначала `programs.niri` (нужен `niri-flake`, в nixpkgs `programs.niri` живёт только на уровне системы и умеет лишь «поставить и включить»), потом `programs.dank-material-shell.niri` (принадлежит модулю `dms.homeModules.niri`, который я убрал, а блок оставил).

Подсказка `Did you mean ...` в конце ошибки — это список реально объявленных соседних опций. Ей стоит верить.

## `attribute 'X' missing` против `undefined variable 'X'`

- **undefined variable** — переменной нет в области видимости. Обычно забыт аргумент в шапке файла: `{ config, pkgs, lib, inputs, ... }:`
- **attribute missing** — объект есть, поля в нём нет. Обычно забыт input во `flake.nix`.

Так вылезло `attribute 'nixpkgs-unstable' missing`: оверлей ссылался на input, которого в inputs не было.

## `file not found`, хотя файл лежит на диске

Flake в git-репозитории видит **только файлы, известные git**. Новый файл без `git add` для Nix не существует. Коммит не обязателен, индекса достаточно.

## `warning: Git tree is dirty`

Не ошибка. Значит, есть незакоммиченные изменения и сборка не привязана к коммиту. Собирается то, что на диске.

## `evaluation warning: 'greetd.tuigreet' was renamed to 'tuigreet'`

Пакеты переезжают между релизами. Пока warning, в следующем релизе станет ошибкой. Чинить сразу, чтобы не копить.

## Home-manager делает файлы read-only

Всё под управлением home-manager — симлинк в `/nix/store`. Поэтому `~/.config/niri/config.kdl` намеренно оставлен обычным файлом: правки применяются мгновенно, `niri validate` работает, пересборка не нужна. Переводить под home-manager, когда конфиг устаканится.

## Claude Code не может обновить сам себя

В `/nix/store` писать нельзя, автообновление молча фейлится. Это нормально: обновление через `nix flake update` + пересборку. Пакет берётся из `nixpkgs-unstable` через оверлей `pkgs.unstable.*`, чтобы не протухал на стабильной ветке.

## `Unable to open a connection to X` под niri

У niri **нет встроенного XWayland**. Любое X11-приложение (Steam, старые игры
и тулкиты) не находит `DISPLAY` и либо падает, либо показывает ровно это окно.

Лечение: поставить `pkgs.xwayland-satellite` — niri сам запустит его при
старте сессии, если найдёт бинарь в `PATH`, и выставит `DISPLAY` потомкам.
Ключ `-listenfd` в `pgrep -af xwayland-satellite` подтверждает, что процесс
поднял композитор.

**Принцип:** под Wayland нехватка системного куска выглядит не как «пакет не
найден», а как «приложение не стартует». Первым делом `echo $DISPLAY`.
Разбор — [[deskjet]].

## Портал на niri неполный: ScreenCast есть, RemoteDesktop нет

`xdg-desktop-portal-gnome` работает поверх Mutter-овских шинных интерфейсов,
а niri реализует из них только один:

```bash
busctl --user status org.gnome.Mutter.ScreenCast     # PID niri — есть
busctl --user status org.gnome.Mutter.RemoteDesktop  # No such device — нет
```

Поэтому всё, что захватывает экран **через RemoteDesktop** (Sunshine в режиме
`capture = portal`), на niri не заведётся, хотя сам сервис поднимется и порты
откроет. Замена — `wlr-screencopy` (`zwlr_screencopy_manager_v1`), его niri
поддерживает. Разбор — [[deskjet]].

## Конфиги из `/home` переезжают вместе с багами

`/home` перенесён с Arch целиком — вместе с ним приезжают `~/.config/*`,
рассчитанные на **другую** систему. Sunshine привёз `portal_token` от чужого
backend'а портала и получил `Restore token is not a valid UUID string`.

Второй случай того же рода — переменные окружения, разобран ниже.

**Принцип:** если сервис ведёт себя странно сразу после переезда, смотреть не
только на nix-конфиг, но и на состояние в `/home`. Оно старше системы.

### Тот же класс: `TERMINFO_DIRS` и ncurses по ssh

**Симптом.** По ssh на deskjet любая ncurses-программа не стартует:

```
ncurses: cannot initialize terminal type ($TERM="xterm-ghostty"); exiting
```

**Ложный след.** Выглядит как «ghostty не установлен на дальней машине» или
«terminfo не завезли». На самом деле файл на диске был — в профиле
пользователя, `/etc/profiles/per-user/gadjet/share/terminfo/x/xterm-ghostty`.

**Причина.** `~/.config/zsh/conf.d/hyde/env.zsh` — остаток набора HyDE,
приехавший вместе с `/home` с Arch, — затирал список каталогов:

```sh
TERMINFO_DIRS="$XDG_DATA_HOME"/terminfo:/usr/share/terminfo
```

Оба пути на NixOS не существуют: `/usr/share/terminfo` там нет в принципе.
NixOS правильно выставляет `TERMINFO_DIRS` в `/etc/set-environment`, но zsh
затирал значение уже после этого. Сравнить:

```
kitjet  (bash): …/.nix-profile/…:/etc/profiles/per-user/gadjet/…:/run/current-system/sw/…
deskjet (zsh):  /home/gadjet/.local/share/terminfo:/usr/share/terminfo
```

**Лечение.** Дописывать к унаследованному, а не затирать. Строкой выше в том
же файле для `XDG_DATA_DIRS` так и сделано — там просто забыли:

```sh
TERMINFO_DIRS="$XDG_DATA_HOME/terminfo${TERMINFO_DIRS:+:$TERMINFO_DIRS}"
```

Плюс `ghostty.terminfo` в `environment.systemPackages` (`modules/common.nix`):
тогда терминал известен системно, а не только в профиле одного пользователя —
иначе то же самое повторится при входе под root.

**Быстрый обход, если правки ещё нет:**

```bash
TERM=xterm-256color nano файл        # разово
ssh -t <хост> env TERM=xterm-256color nano файл
```

**Для Ubuntu (`pintu`)** пакета в репозиториях нет — описание терминала
переносится с машины, где ghostty есть:

```bash
infocmp -x xterm-ghostty | ssh pintu -- tic -x -
```

**Вывод шире частного случая.** `/home` переехал с Arch целиком, и вместе с
ним — конфиги, которые считают, что вокруг Arch. Переменные вида
`PATH`, `XDG_DATA_DIRS`, `TERMINFO_DIRS`, `LD_LIBRARY_PATH` в таких конфигах
надо проверять на безусловное присваивание:

```bash
grep -rnE '^[A-Z_]+=.*(/usr/|/opt/)' ~/.config/zsh/conf.d/ ~/.zshrc ~/.profile
```

## `switch` прошёл, а система `degraded`

`nixos-rebuild switch` заканчивается успехом, если **собралось и применилось**.
Упавший после этого юнит на код возврата не влияет — о нём никто не скажет.

Так на kitjet больше суток жил `podman-homeassistant.service`, падавший на
несуществующем `/dev/ttyACM0`: блок приехал копипастой из вики (там прямо
написано «Example, change this to match your own hardware»), а настоящий
Home Assistant — в VM. Разбор — [[Home-Assistant]].

Проверять после каждого `switch`, на обеих машинах:

```bash
systemctl is-system-running    # running / degraded
systemctl --failed
```

**Принцип:** копипаста из вики опасна не тем, что не работает, а тем, что
работает наполовину — сервис объявлен, юнит создан, и он честно падает в
цикле. Удалять примеры целиком, а не править под себя, если функция не нужна.

## Обозначения на будущее

- `stateVersion` — не версия ОС, а маркер формата данных. Не менять никогда.
- `hostId` — по нему ZFS решает, её ли пул. Уникален на каждой машине.
- Систему в NixOS почти нельзя уронить насмерть: старое поколение выбирается в меню загрузки.
