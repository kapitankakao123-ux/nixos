# Структура репозитория и команды

## Раскладка

```
~/nixos/
├── flake.nix              # хосты объявлены ОДИН раз → nixosConfigurations + ноды colmena
├── flake.lock             # точные коммиты всех inputs. Коммитить обязательно
├── modules/               # ЧТО машина умеет
│   ├── common.nix         #   nix, локаль, юзер, ssh — на всех
│   ├── desktop.nix        #   niri + DMS + звук + шрифты + home-manager
│   ├── storage.nix        #   ZFS, samba/nfs
│   ├── virtualisation.nix #   libvirt/KVM
│   ├── kiosk.nix          #   cage + браузер на весь экран (rpinix)
│   └── backup.nix         #   sanoid + syncoid
├── home/                  # окружение пользователя
│   ├── common.nix         #   DMS и дотфайлы — одинаковые везде
│   ├── kitjet.nix
│   └── deskjet.nix
├── hosts/                 # КАКАЯ машина что из этого включает
│   ├── kitjet/{default.nix, hardware-configuration.nix}
│   ├── rpinix/default.nix
│   └── deskjet/{default.nix, hardware-configuration.nix}
└── docs/                  # этот vault
```

Правило раскладки: `modules/` — возможности, `hosts/` — их выбор. Новая общая настройка идёт в `modules/`, специфика машины — в `hosts/`.

## Роли файлов

- **flake.nix** — источники (`inputs`) и что собирать (`outputs`). Пакетов в нём нет.
- **configuration.nix / hosts/\*** — система: ядро, драйверы, службы, пользователи. Всё, что от root, до логина или общее для всех.
- **home/\*** — пользователь: `~/.config`, дотфайлы, прикладные программы.

Критерий, куда класть пакет: нужен от root, до логина, тянет systemd-юнит или udev-правила → система. Иначе → home.

## Где живёт сам репозиторий

Вопрос «локально или в интернете» — ложная дихотомия: в git копия есть на каждой машине, где ты его клонировал. Разница только в том, **какая копия считается точкой обмена** (remote), через которую машины видят правки друг друга.

Раскладка:

- **Рабочая копия — на той машине, за которой сидишь и с которой деплоишь.** Сейчас это `kitjet:~/nixos`. Когда поднимется `deskjet` — там будет свой клон того же репозитория. Напрямую друг с другом они не синхронизируются, только через remote.
- **`rpinix` клон не нужен.** Colmena собирает конфиг на машине-деплойере и отправляет готовые пути по ssh; на целевой ноде git не требуется.
- **Сборка идёт из локального пути** (`nixos-rebuild switch --flake ~/nixos`), а не из URL. Иначе каждую правку пришлось бы коммитить и пушить до проверки.

Решение: **`origin` — приватный репозиторий на GitHub, плюс зеркало bare на `kitjet`.**

Почему нужен именно интернет-remote, а не только bare-репозиторий дома:

- Установка `deskjet`/`rpinix` начинается с «достать конфиг». Если единственная копия лежит на `kitjet`, а он выключен или как раз переустанавливается — остаёшься с флешкой и без конфига.
- Offsite-копия: пожар, кража или сдохший NVMe не уносят с собой всю инфраструктуру.
- Доступ снаружи дома, без VPN.

Приватный хостинг безопасен при соблюдении правила «секреты в git не кладём»; после подключения `sops-nix` секреты попадут в репозиторий уже зашифрованными — это нормально даже для публичного репо.

Зеркало на `kitjet` — на случай, когда интернета нет, а собрать надо:

```bash
# на kitjet, один раз
git init --bare /tank/git/nixos.git

# в рабочей копии
git remote add origin git@github.com:<логин>/nixos.git
git remote add kitjet /tank/git/nixos.git
git push origin main && git push kitjet main
```

`/tank/git` — датасет ZFS, значит он попадает в снапшоты sanoid и в реплику на `rpinix` вместе с остальными данными. Отдельного бэкапа репозиторию не нужно.

**Vault `docs/` кладём в тот же репозиторий**, а не рядом: заметки описывают ровно то состояние конфига, что лежит в соседних файлах, — расходиться им незачем, и вопрос «где бэкап vault» закрывается тем же push.

## Команды

```bash
colmena apply                 # раскатать на все машины
colmena apply --on rpinix       # на одну
colmena apply-local           # на ту, за которой сидишь
colmena build                 # только собрать, не катить

sudo nixos-rebuild switch --flake ~/nixos          # локально, по hostname
sudo nixos-rebuild test --flake ~/nixos            # применить до перезагрузки
nix flake update                                   # обновить все inputs
nix flake update nixpkgs                           # обновить один
nix flake show ~/nixos                             # какие конфигурации объявлены
```

Рабочий цикл: правка → `git add` новых файлов → сборка → если завелось, `git commit`. Коммит **после** успешной сборки, чтобы в истории лежали только рабочие состояния.

## Развёртывание: colmena

> Включена 2026-09-13. До этого деплой был только локальный.

### Почему не `nixos-rebuild --flake .#<имя>`

**Имя после `#` — это имя конфигурации во flake, а НЕ адрес машины.**
Команда `nixos-rebuild switch --flake .#deskjet`, запущенная на kitjet,
соберёт конфиг deskjet и применит его **к kitjet**: тот сменит hostname,
ключи, ядро — буквально превратится в deskjet. Ошибка обидная и тихая:
команда отработает успешно.

Чтобы попасть на удалённую машину, цель надо назвать явно:

```bash
nixos-rebuild switch --flake .#deskjet --target-host root@deskjet.local
```

У colmena цель прописана в самой ноде (`deployment.targetHost`), поэтому
перепутать нельзя в принципе — это и есть главный довод за неё.

### Как устроено

Выход `colmena` в `flake.nix` генерируется из того же `hosts`, что и
`nixosConfigurations`. Список модулей машины вынесен в `hostModules` и
используется обоими — «что входит в машину» описано в одном месте.

`rpinix` в деплой не входит (`deployHosts` его отфильтровывает): железо
теперь под Ubuntu, а конфиг оставлен на случай возврата.

```bash
colmena apply --on deskjet                      # одна машина
colmena apply                                   # все
colmena build                                   # только собрать
colmena apply-local --sudo                      # та, за которой сидишь
colmena exec --on deskjet -- systemctl --failed # команда на машинах
```

Собирается всё на той машине, где запущена команда; на цель уезжает
готовый результат. Запускать можно с любой из двух — проверено в обе стороны.

### Имена вместо адресов

`deployment.targetHost = "<имя>.local"`. Адреса от DHCP у нас менялись
несколько раз, поэтому не IP. Имена `.local` разрешаются через mDNS —
в `modules/common.nix` включён avahi:

```nix
services.avahi = { enable = true; nssmdns4 = true; openFirewall = true; };
```

**`nssmdns4` обязателен.** Без него демон работает и машину видно снаружи,
но сама она чужие `.local` не разрешает: в `/etc/nsswitch.conf` не
появляется `mdns4`. Симптом был именно такой — deskjet отвечал на mDNS
(avahi там включал Sunshine для Moonlight), а kitjet его не находил.

Проверка: `getent hosts deskjet.local`.

### Почему короткое имя не работало

`getent hosts deskjet.local` отвечал, а `ssh deskjet` и `ping deskjet` —
нет. **mDNS обслуживает только имена на `.local`**, голое `deskjet` для него
не имя. Короткие имена даёт DNS роутера.

Роутер знал `kitjet` и `pintu`, но не `deskjet`. Причина — в обратной записи:

```bash
dig +short @192.168.10.1 -x 192.168.10.125   # GadjetArch.gadjet
dig +short @192.168.10.1 -x 192.168.10.20    # Kitjet.gadjet
```

Роутер держит **аренду со времён Arch** и зовёт машину прежним именем
`GadjetArch`, новое не перезаписывает. Лечится на роутере: удалить аренду
для `.125`, после чего deskjet зарегистрируется заново.

Со стороны NixOS нужно было одно — чтобы NM вообще отправлял имя:

```nix
networking.networkmanager.settings.connection."ipv4.dhcp-send-hostname" = true;
```

NM 1.52+ по умолчанию его НЕ шлёт. У `kitjet` и `pintu` сеть настраивает
не NetworkManager, поэтому они зарегистрировались сами — отсюда и разница.

**Ключ именно `dhcp-send-hostname`, без `-v2`.** Вариант с суффиксом NM 1.56
не понимает: пишет `config: unknown key` в журнал и молча игнорирует
настройку. Проверять так:

```bash
journalctl -u NetworkManager --since -1min | grep -i "unknown key"
```

Пока аренда на роутере не почищена, короткие имена подставляет
`~/.ssh/config` из home-manager (`programs.ssh.matchBlocks`):
`ssh deskjet` → `deskjet.local`. Для `ping` по-прежнему нужен `.local`.

**Отвергнутая версия:** добавить `local` в `search`. Не работает —
дополнение короткого имени до `deskjet.local` делает только модуль `dns`,
и запрос уходит на роутер, который такого имени не знает. mDNS в
дополнении имён не участвует. Проверено.

### Доступ

colmena ходит на цель как **root** по ssh-ключу. Ключи обеих машин
прописаны в `modules/common.nix` и раздаются декларативно
(`/etc/ssh/authorized_keys.d/root`), руками в `/root/.ssh` класть не нужно.

Запускает команду `gadjet` и использует **свой** ключ — поэтому
`ssh root@kitjet.local` из-под root на deskjet не работает и не должен:
у root приватного ключа нет, пара принадлежит пользователю.

**Первый деплой на новую машину** — курица и яйцо: ключ root'а появится
только вместе с конфигом, который ещё надо доставить. Разрывается разово:
положить ключ в `/root/.ssh/authorized_keys` по паролю, развернуть, затем
файл удалить — дальше ключи приходят из конфига.

### Метка версии отличается

`nixos-version` после colmena показывает `26.05pre-git`, после
`nixos-rebuild` — `26.05.20260905.6713828`. Косметика: colmena импортирует
nixpkgs напрямую, без метаданных flake. Но верхушка системы при этом
другая, поэтому чередование инструментов каждый раз пересобирает
последний слой. Лечится выбором одного инструмента.

## Работа с git на двух машинах

> Записано 2026-09-13 после того, как репозиторий разъехался между kitjet
> и deskjet, а при объединении в `modules/common.nix` закоммитились маркеры
> конфликта — и master перестал собираться.

### Что произошло и почему это не «две ветки»

Ветка одна — `master`. Просто рабочих копий стало две, и каждая жила
своей жизнью. Разъехаться они могут по-разному, и лечится это по-разному:

```bash
git merge-base --is-ancestor <их-коммит> <наш-коммит> && echo "просто отстал"
```

- **Отстал** (коммит одной машины — предок другой): сливать нечего, `git pull`.
- **Разошлись** (у обеих есть свои коммиты): нужен merge или rebase.

В нашем случае deskjet просто отстал на 4 коммита: его ссылка `origin/master`
устарела, потому что после пуша он ни разу не делал `fetch`. Сравнивать надо
не `git status` (он врёт про синхронизацию, если давно не забирал), а хеши:

```bash
git ls-remote origin master   # что на самом деле на GitHub
git log --oneline -1 HEAD
```

### Порядок, при котором это не повторяется

1. **Перед правкой — всегда `git pull`.** Не «когда вспомню», а первым делом.
2. **После коммита — сразу `git push`.** Коммит, который лежит только на одной
   машине, и есть будущее расхождение.
3. **Правки вносить на одной машине.** Вторую обновлять деплоем по сети
   (`nixos-rebuild --target-host`, позже colmena), а не отдельной копией
   репозитория. Одна рабочая копия — расходиться нечему.
4. **Линейная история по умолчанию:**

```bash
git config --global pull.rebase true
```

### Защита от главной ошибки

Маркеры конфликта, попавшие в коммит, ломают конфиг молча: `git status`
покажет «clean», а сборка упадёт. В репозитории лежит хук, который такой
коммит не пропускает. **Включить на каждой машине один раз:**

```bash
git config core.hooksPath .githooks
```

Хуки не переносятся через `clone` сами — `.git/hooks` не версионируется.
Поэтому они лежат в `.githooks/`, а команда выше говорит git брать их оттуда.

Проверить руками, без хука:

```bash
git diff --check                                  # перед коммитом
grep -rn "^<<<<<<< \|^>>>>>>> " --include="*.nix" .   # в рабочем дереве
```

### Разрешение конфликта по шагам

1. `git status` — какие файлы конфликтуют.
2. Открыть файл: между `<<<<<<<` и `=======` — твой вариант, между
   `=======` и `>>>>>>>` — чужой.
3. Оставить нужное, **удалить все три строки-маркера**.
4. `git add <файл>`, затем `git rebase --continue` или `git commit`.
5. **Собрать до пуша** — `nix build .#nixosConfigurations.<хост>.config.system.build.toplevel`.
   Правило «коммит после успешной сборки» существует ровно для этого.

### Push на GitHub

Настроено 2026-09-13: `origin` по SSH, ключи машин зарегистрированы
в GitHub. `git push` идёт без ввода токена.

```bash
git remote -v                     # должен быть git@github.com:...,  не https://
ssh -T git@github.com             # ждём «Hi <логин>!»
```

## Правила, нарушение которых стоит вечера

- **`git add` для каждого нового файла.** Flake в git-репозитории видит только файлы, известные git. Не добавил — «file not found», хотя файл лежит на диске. Коммит не нужен, индекса достаточно.
- **`networking.hostId` уникален на каждой машине.** По нему ZFS решает, её ли это пул.
- **`system.stateVersion` не меняется никогда.** Это маркер формата данных, а не версия ОС.
- **Имя после `#` — это имя конфигурации во flake**, не хост и не пользователь. Совпадает с `networking.hostName` → можно опускать.
- **`git pull` перед правкой, `git push` сразу после коммита.** Коммит, лежащий только на одной машине, — это будущее расхождение.
- **Маркеры конфликта не должны попасть в коммит.** `git status` покажет «clean», а сборка упадёт. Защита — хук: `git config core.hooksPath .githooks`.
- **Секреты в git не кладём.** До появления `sops-nix` — только пути к файлам вне репозитория.
